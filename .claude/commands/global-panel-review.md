description: Stack-agnostic 5-reviewer panel on the branch diff — consolidate, senior-dev plan, tracked tech-debt doc. Generic fallback; prefer /panel-review in this repo.
---

Run a **multi-perspective review panel** on the current branch's changes, then synthesize the findings into a prioritized, actionable fix plan. Five specialist reviewers each critique the diff from a distinct hat; you collate every concern in priority order, then put on a **senior developer** hat to turn them into a plan — and you may override any finding with a clearly-reasoned justification.

**All findings + the plan are written to a tracked Markdown doc** (not just printed in chat) so it can feed a future tech-debt sprint. Every finding gets a **stable ID** and a **status marker** that is ticked off as the work gets done.

This skill is **stack-agnostic** — it adapts to whatever language, framework, and tooling the current repo uses. Detect the project's stack and conventions instead of assuming any.

> **This is the canonical template.** It runs standalone in any repo. In THIS repo prefer **`/panel-review`**, the tailored copy generated by `/init-panel-review`, which bakes in the concrete base branch, safe test commands, the Playwright capture recipe, and the house conventions — so each run skips re-detection. Keep this file as the source of truth; when it improves, re-run `/init-panel-review` to refresh the tailored copy.

Scope: by default review what changed on this branch vs the repo's base branch. If `$ARGUMENTS` names a base ref (`vs develop`), an area/path, or both, honor it.

## 1. Establish scope (do this first, once, in the main thread)

- **Pick the base ref.** Use `$ARGUMENTS` if it names one; else the repo's default branch (`git symbolic-ref refs/remotes/origin/HEAD` — often `main`/`master`; fall back to `main`, then `master`, then `develop`). Compute the comparison from the merge-base.
- **Capture the full changed surface, including uncommitted work** (a branch may have no commits yet):
  - Committed: `git diff <base>...HEAD --stat` and `git diff <base>...HEAD`.
  - Working tree: `git diff <base> --stat` and `git status --porcelain`. **New/untracked files won't appear in `git diff` — read them directly.**
- **Learn the project's conventions and stack.** Read any of these that exist: `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING*`, `README*`, `.editorconfig`, lint/format configs, and manifests (`package.json`, `*.csproj`, `pyproject.toml`/`requirements*.txt`, `go.mod`, `Cargo.toml`, `Gemfile`, `pom.xml`/`build.gradle`, `Makefile`). From these, identify: the languages, the **test runner(s)**, how the **UI is rendered/previewed** (if any), and the house style/architecture rules to hold the code to.
- List the changed files and the new/changed **public surfaces** (endpoints/APIs, DB schema/migrations, CLI, exported modules) and **UI screens/routes**. Note mobile vs desktop targets if relevant.
- Pass this scope (file list + the diff command to use + detected conventions/stack) into every subagent prompt so they all review the same surface.

## 2. Launch the panel — five subagents, concurrently

Spawn all five in a **single message** (parallel) as **general-purpose** agents. Give each the scope from step 1, tell them to read the actual diff (committed + working-tree + untracked new files) and cite `file_path:line`, and this **output contract**:

> Return a list of concerns. For each: a **severity** (P0 blocks/incorrect · P1 clearly hurts · P2 polish), the `file:line`, the problem, *why it matters*, and a **concrete fix**. End with your single highest-leverage item. Be specific and honest; no flattery. Do not edit code.

### Reviewer A — Principal Software Engineer (architecture & code quality)

Strict principal-engineer hat. Review the changed code against:

- **SOLID** — single responsibility (god classes/functions/components? handlers doing too much?), open/closed, dependency inversion (concretions vs abstractions), interface segregation.
- **DRY** — duplicated logic/markup/constants that should be shared; copy-paste across files.
- **KISS** — unnecessary complexity, cleverness, over-abstraction, dead branches.
- **SoC** — layering/boundaries respected for *this* stack (presentation vs domain vs data; no business logic in controllers/views; no leaky abstractions; data access where it belongs).
- **YAGNI** — speculative/unused code. **Mark YAGNI findings as the lowest priority** (cap at P2 unless they actively cause a bug).

**Hold the code to the project's own documented conventions** (from the files read in step 1) and call out violations, plus dead code, missing error handling, and (if the stack has a compiler/linter) anything that would warn.

### Reviewer B — UI/UX Engineer (visual & interaction quality)

Only if the change touches UI. Prefer judging from **real rendered output**, not code alone:

- Detect how this project renders UI and use it to capture screenshots — a dev server + browser-driver (Playwright/Cypress/Puppeteer), Storybook, or a built preview. Reuse existing test fixtures/mocks/seed data. If a fixed port is occupied, start on a free one and **revert any config change** after. Capture desktop **and** mobile widths for anything responsive, and open key dialogs/states (empty, loading, error). Write any capture/harness file to a **temp location and delete it when done**.
- If there is no practical way to render the UI, review from the changed markup/styles + existing visual tests, and **say explicitly that you reviewed from code, not screenshots.**

Assess: **consistency** (matches the app's design system / shared components; no one-off colors/sizes/raw elements where a primitive exists), **layout not overwhelming** (spacing, rhythm, no cramped clusters or wasted space), **primary action stands out naturally** (one clear primary per view; not buried in an equal-weight row), **typography scaled** (hierarchy, readable sizes, contrast, no truncation), **accessibility** (labels/aria on icon-only controls + inputs, focus order, **never color-only** status, adequate tap targets on touch), and **responsive/mobile** behavior. Honor any UI rules in the project's convention docs.

### Reviewer C — First-time user (clarity & friction)

Adopt a brand-new user with no training and no tribal knowledge. From the screens/flows/CLI and the changed copy/labels, assess: **clarity** (is it obvious what each control/option does and what happens next?), **onboarding friction** (dead ends, hidden prerequisites, undiscoverable steps, anything that forces a guess or a "go ask someone"), and **terminology** (jargon, abbreviations, ambiguous labels, inconsistent naming for the same concept, unlabeled codes). For each: what confused you, why, and a concrete wording/UX fix (label, helper text, empty-state copy, ordering).

### Reviewer D — Senior QA Automation & Test Engineer (correctness coverage)

Review the changed code **and** the changed/added tests together. **Detect and run the project's test suite(s)** (e.g. `npm/pnpm/yarn test`, `dotnet test`, `pytest`, `go test ./...`, `cargo test`, `make test`) and report pass/fail; if a suite needs a service/port, start it on a free port and revert after.

> **Safety gate:** before running any suite, determine what database/state it writes to. If the suite runs against a shared or development database rather than a disposable/test one, **do not run it** — review coverage on paper instead and say so. A test suite with unscoped cleanup can destroy real data.

Determine whether the tests actually exercise: **data validation** (required fields, bounds, bad/duplicate input, type/format), **state management** (persistence, restore, stale state, concurrency/idempotency), **error handling** (failures, partial failures, not-found/forbidden, timeout/network), and **edge cases** (empty/large/boundary, auth/role gating, soft-delete, mixed states). For each gap, name the **untested path** (`file:line`) and the **specific test that should exist**. Distinguish "covered / partially / not covered".

### Reviewer E — Principal Software Architect (systems: extensibility, scale, security, blast radius)

Step back from line-level code to the **system** the change creates or touches. Assess:

- **Extensibility & boundaries** — are module/service boundaries clean and stable? Is new behavior added by *extension* or by editing core (open/closed at the system level)? Leaky abstractions, tight/circular coupling, a change that will be expensive to evolve, seams in the wrong place, public contracts (APIs/schemas/events) that lock in a shape that's hard to version.
- **Scalability & performance** — concrete bottlenecks: **N+1 queries** (per-row/per-iteration queries, ORM lazy-load in loops), **unbounded result sets / missing pagination**, hot loops, synchronous/blocking I/O on a request path, chatty cross-service calls, missing/oversized indexes implied by new queries. **DB locking/contention risks**: long-running or wide transactions, table/row locks, `SELECT … FOR UPDATE`, write-amplification, deadlock-prone ordering. **Horizontal-scaling blockers**: in-process or static mutable state, singletons holding state, local-only caches/locks, sticky-session assumptions, single-instance background workers/schedulers, non-idempotent handlers, ordering assumptions that break with >1 instance.
- **Security & compliance** — is sensitive data (PII, secrets, credentials, tokens) handled correctly: never logged or committed, redacted, encrypted at rest/in transit, least-privilege? Authn/authz enforced on every new surface (not just the UI)? Injection / SSRF / path-traversal / deserialization exposure? Anything that breaks the project's data-handling or compliance rules.
- **Blast radius & resilience** — if this component (or a dependency it adds: DB, external API, queue, device, cache) **fails or goes slow**, what breaks and how far does it spread? Are failures contained (timeouts, bounded retries w/ backoff, circuit-breaking, graceful degradation, idempotency, partial-failure handling) or do they cascade? Any new **single point of failure**, or work that isn't recoverable/resumable after a crash mid-operation?

Give each finding a concrete fix (a boundary to introduce, a query to batch, state to externalize, a timeout/limit to add, a secret to move).

## 3. Consolidate — all concerns, one priority-ordered list

Merge the five reports into a **single list ordered by priority** (P0 → P1 → P2; within a tier, correctness/safety before polish). De-duplicate where reviewers overlap (note "raised by A+B"). Keep YAGNI items at the bottom. Don't drop anything. Assign each finding a **stable ID** `F-NNN` (zero-padded, never reused) — this is how it's referenced in commits/sprints later.

## 4. Senior-developer synthesis — the plan

Wear the **senior developer** hat and turn the consolidated list into an execution plan:

- Group findings into **batches** (e.g. "correctness/test gaps", "UX consistency", "copy/terminology", "cleanup") and order the batches by value-vs-effort.
- For each item give a **fix priority** (Now / Next / Later) and a rough effort (S/M/L).
- **Overrides:** you may reject or downgrade any reviewer's finding — but only with an explicit, spelled-out reason (e.g. "intended per the project's documented rule X", "matches the established pattern, churn not worth it", "YAGNI — speculative, no bug"). Record overrides as findings with status `Overridden` (don't delete them — the reasoning must stay auditable).
- End with the recommended first PR's worth of work (the "do these now" set).

## 5. Write the tracked doc (the deliverable)

Persist everything to **`docs/tech-debt/panel-review-<branch>.md`** (create `docs/tech-debt/` if missing; `<branch>` = current git branch, with `/` replaced by `-`). **If the file already exists, UPDATE it in place — preserve every existing `Done`/`Overridden` marker and its "Handled:" note; only add new findings (continue the `F-NNN` numbering) and refresh the plan.** Never renumber or silently drop a previously-recorded finding.

Doc structure:

- **Header:** branch, review date (absolute), base ref + diff command, one-line scope (areas reviewed), detected stack, and the suite status at review time (which suites ran + pass counts, or "not run / none found").
- **Status legend:** `- [ ]` Open · `- [x]` Done · `- [x] ~~…~~ (Overridden)` rejected/downgraded by senior-dev with reason.
- **Findings** — one checkbox line per finding, each carrying its ID, priority, hat, and location, e.g.:

  ```
  - [ ] **F-001** · P0 · Eng · `path/to/file.ext:120-180` — <concern>.
        _Why:_ <one line>  _Fix:_ <concrete fix>  _Handled:_ —
  ```

  When an item is completed later, flip `- [ ]`→`- [x]` and fill `_Handled:_` with the **absolute date + commit/PR ref** (e.g. `_Handled:_ 2026-06-20, PR #231`). Overridden items use `- [x] ~~F-0NN ...~~ (Overridden: <reason>)`. **Leave these markers as the single source of truth a tech-debt sprint reads.**
- **Implementation plan:** the batches (Now/Next/Later, effort) referencing finding IDs, and the recommended first PR.
- **Overrides:** listed (also reflected as `Overridden` findings above).

Print a short summary in chat (counts by priority + the "do now" set) and link the doc path.

## Rules

- **Review only — do not implement fixes** unless the user explicitly asks afterward. (Writing/updating the tracked doc is expected; it is not a code change.)
- Cite `file_path:line` throughout. Prefer concrete fixes over vague advice.
- Clean up any temporary specs/files and revert any temporary config (ports, etc.) before finishing.
- The doc's checkbox/`Handled` markers are durable — whoever later fixes a `F-NNN` item should tick it and record the commit, so the doc always shows what's left vs done.
