## Phase 2 — Template-literal → cn() codemod

### Task 2.1: Build the codemod

- [ ] **Step 1: Write the codemod script**

Create `scripts/codemods/sweep-classname-template-literals.ts`. Pattern: match `className={\`{base} ${cond ? "a" : "b"} ${other}\`}` (the simple shape) and rewrite to `className={cn("{base}", cond ? "a" : "b", other)}`. Skip:
- Template literals containing function calls or computed expressions inside `${...}` beyond simple ternary
- Multi-line template literals (would risk reformatting)
- Files where `cn` would conflict with an existing import (auto-add `import { cn } from "@/utils/cn"` if absent)

Use the same `runCodemod` infrastructure as Plan 1's sweep-* scripts. Reference `scripts/codemods/sweep-brand-red.ts` for shape.

- [ ] **Step 2: Add npm scripts to package.json**

```json
"sweep:classname-templates": "tsx scripts/codemods/sweep-classname-template-literals.ts --apply",
"sweep:classname-templates:dry": "tsx scripts/codemods/sweep-classname-template-literals.ts",
```

### Task 2.2: Dry-run + sanity-check

- [ ] **Step 1: Dry-run**

```bash
npm run sweep:classname-templates:dry > /tmp/classname-templates-plan.txt 2>&1
wc -l /tmp/classname-templates-plan.txt
head -50 /tmp/classname-templates-plan.txt
tail -30 /tmp/classname-templates-plan.txt
```

Expected: ~400-700 replacements (audit estimated 704 template-literal sites; codemod's conservative shape may match fewer).

- [ ] **Step 2: Spot-check 10 random replacements**

Verify the rewrite is byte-equivalent CSS-wise. Common pattern:
- BEFORE: `` className={`base ${active ? "bg-red-600" : "bg-gray-100"}`} ``
- AFTER: `` className={cn("base", active ? "bg-red-600" : "bg-gray-100")} ``

If anything looks mangled (e.g. `cn(` not closed properly, missing arg, wrong import path), STOP and fix the codemod.

## Phase 4 — `audit-decomposition` codemod

### Task 4.1: Build the screening codemod

- [ ] **Step 1: Write `scripts/codemods/audit-component-decomposition.ts`**

Walks `src/components/**/*.tsx` and `src/app/**/*.tsx`. For each file, scores against the criteria in [component-decomposition-criteria.md](../../shared-ui/component-decomposition-criteria.md):

**Strong signals (1 point each, 1+ = candidate):**
- File contains `<style jsx>` or `<style>` block >200 LOC
- Contains `:global(...)` selectors
- Contains 3+ inline SVG icon factory functions (`function .*Icon(`)
- File LOC >800
- Contains 4+ top-level conditional render branches in a single return
- Multiple distinct concerns (data fetching + business logic + presentation in one file — heuristic: `useEffect` count + `useState` count + helper function count)

**Weaker signals (0.5 points each):**
- File LOC 500-800
- 20+ arbitrary-value classNames
- Any single className attr >300 chars
- Long inline `style={{}}` objects (5+ properties at multiple call sites)
- 5+ `useState` slices

Output: `docs/shared-ui/decomposition-backlog.md` with shape:

```markdown
# Component Decomposition Backlog

Generated: 2026-05-08 by `npm run audit:decomposition`.

## High priority (5+ signals)

- [path/to/file.tsx](path/to/file.tsx) — 7 signals — 1495 LOC, has <style jsx> 900 LOC, 9 SVG factories, ...

## Medium priority (3-4 signals)

...

## Low priority (1-2 signals)

...
```

- [ ] **Step 2: Add npm script**

```json
"audit:decomposition": "tsx scripts/codemods/audit-component-decomposition.ts",
```

### Task 4.2: Run the audit + check the output

- [ ] **Step 1: Run audit**


- [ ] **Step 2: Read the backlog**

Confirm `docs/shared-ui/decomposition-backlog.md` was generated. Top entries should match the audit findings (UserDetailModal, UsersManagement, Header for the High priority section).
